基于一次机会，我同时了解到了多发选收技术和eBPF技术，并考虑如何将两者结合起来。我的整个实践在两个openwer虚拟机上实现，其实本质上还是在linux上进行的。

这里的多发选收指的是两个网络设备之间，发送端通过多个不同的物理链路同时发送二层数据包，例如蜂窝网络、wifi和有线网络，在接收端对收到的数据包进行选优和去重，这里的选优其实就是**先到先选**。其实对于linux来说多发并不困难，linux提供了接口bonding功能，可以将多个二层网络接口聚合成一个接口，配置广播策略后即可实现二层数据包多发功能。问题还是聚焦在选收上，在接收端需要将第一个包到达后的相同包丢弃。

基于前面我们的分析，不难得出问题的关键在于：

1. 我们如何得知区分不同链路收到的数据包是否是同一个包。
2. 使用什么数据结构记录已经收到的包，以便后续包抵达时进行区分。
3. 在什么样的层级上进行上述操作，以便将对网络性能的影响降到最低。

## 数据包唯一标识

考虑遵循IEEE 802.3标准的以太网帧，即二层数据包。

在以太网帧定义上其实有一个很好的字段可以用来标识每个数据包，即帧尾的CRC32循环冗余校验码，
这个校验码的计算内容包括帧头和载荷，尽管这个校验的作用是进行纠错，但是用作简单的唯一标识也是可行的。

遗憾的是，这个校验通常由网卡硬件完成计算并剥离，在我们可处理数据包的最早阶段也无法获取到CRC32校验码。
虽然我们无法获取这个现有的值，但是我们可以由此得到启发，通过某种hash算法对整个数据包做hash，得到一个唯一标识。

由于我们决定使用eBPF程序实现整个选收逻辑，所以我们的hash也要在eBPF程序中完成计算，这意味着我们无法使用硬件加速的hash接口，
整个hash算法都是纯软件完成的，在这个前提下，CRC32算法就显得太重了，进行大量数据包吞吐时，hash算法的性能显得更为关键，
这直接影响整个网络吞吐性能。对于性能的考虑是一方面，另一方面是对于**简单**的考虑，我始终认为eBPF程序应该精简且易懂，
太复杂的hash算法也不在考虑之内。

由此我将目光转向FNV-1a算法，它快速、实现简单并且具有不错的hash分布，这正好符合我们的要求，由此我将它作为第一个选择，至于说它有多简单呢？
不需要你额外的查找资料，下面的代码就是整个算法的一切。

{% highlight rust %}
fn hash_data(data: &[u8]) -> u32 {
	const FNV_PRIME: u32 = 0x1000193;
	let mut hash: u32 = 0x811c9dc5;
	for byte in data {
		hash ^= byte as u32;
		hash = hash.wrapping_mul(FNV_PRIME)
	}

	return hash;
}
{% endhighlight %}

对于hash算法的选择上，FNV-1a不是最好的，它可能不是最快速的，也可能不是最简单的，但是我不希望在hash算法的选择上花费太多时间，所以我选择了它。

现在，我们有了hash算法，距离我们标识一个数据包又近了一步，下一个问题是——我们真的需要对整个负载做hash吗？
